The five findings that changed the build

Each of these overturned something that looked settled.

  1. Most of every chunk was invisible to search

    The encoder caps input at 256 tokens and truncates the rest silently — no error. Chunks were sized in words (500), so the median chunk ran to 626 tokens and 15 of 22 lost ~60% of their content before ever being embedded. The text was stored and citable, but could never influence whether its own chunk was found.

    Fixed by chunking on the tokenizer, plus an assertion that refuses to build an index if any chunk exceeds the ceiling.

  2. A conclusion drawn on a small corpus was backwards

    On one document, hybrid search looked useless — every fusion mode tied. But a 20-candidate pool was 31% of that corpus, so recall was trivially perfect for anything. At 20 documents the pool is 0.84%, and hybrid fusion is worth +13 points of hit rate.

    Three separate conclusions inverted when the corpus grew: whether fusion helps, which fusion to use, and where the abstention threshold belongs.

  3. The metrics reported success on questions the system couldn't answer

    For a question five papers answer, the system returned all five passages from one paper. MRR scored it 1.000; source recall scored it 0.200. Ranking metrics call that perfect — by their definition it is.

    It is the wrong definition for "compile every source". A per-document cap lifted source recall to 0.830 with no loss to ranking, because the cap only skips — it never reorders.

  4. The evaluation tool had a bug in it

    NDCG is normalised and cannot exceed 1.0. Its first run printed 1.373. Page-level relevance let several returned chunks share one gold page, so achieved DCG summed over all of them while the ideal allowed only one.

    Caught only because the output violated a bound the metric is known to have. A metric with no known bounds would have shipped wrong and stayed wrong.

  5. A feature was built, measured, and removed

    Chunks carry no document identity, so passages from similar papers look alike. Prefixing each chunk with its document title should fix that. Reported as a small win — that report was wrong: the prefix arrived alongside a chunk-size change, and the two could not be separated.

    Re-measured with one variable: no effect on ranking, source recall 5 points worse. Every chunk in a document got the same prefix, making them more alike and clustering retrieval harder onto one document. Reverted.

Pending

Ordered by what actually blocks using this on your real documents.

Blocking · your documents

Native Google Docs cannot be read at all

A .gdoc is a ~100-byte JSON file containing a URL. The content is on Google's servers. Nothing local can read one — not this tool, not Word. Ingestion now says so explicitly rather than skipping silently, but the files remain unusable.

Two fixes: export them to PDF/.docx, or add Drive API export-on-fetch (Google Cloud project, OAuth, one new loader path).

How much to trust these numbers

Read before quoting any figure above

Every number is a property of this corpus, not of the code. Three tuned parameters — chunk size, fusion strategy, abstention threshold — each had to be re-derived when the corpus changed, and one conclusion reversed outright. Pointing this at your real documents means re-running python src/evaluate.py, which the harness exists to make a ten-minute check rather than a guess.

23 cases is small. Treat differences under ~0.05 as noise.

The corpus is 20 ML research papers — deliberately similar, which is the hard case, but not contracts, spreadsheets, or scanned reports. Retrieval behaviour on those is untested.

Labels were authored by the same process that built the system. Mitigated by deriving them from the corpus rather than writing them by hand, so they cannot drift — but not eliminated.
