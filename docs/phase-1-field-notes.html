Mechanism Notes · Phases 1–3

Anatomy of a Retrieval Pipeline

A step-by-step account of what actually happens to a PDF as it becomes searchable, and to a question as it becomes a cited answer. This is the Retrieval-Augmented Generation (RAG) pattern: retrieve first, then generate strictly from what was retrieved. Phase 1 builds that pipeline and takes it apart; Phase 2 makes its rankings good and, more importantly, proves it. Every number here is measured from the running system, not estimated — including two defects the measurements exposed, one of them in the measuring tool itself, and one conclusion that turned out to be an artifact of corpus size rather than a property of the method.

Step 01

Parsing — recovering text from a print format

Turning a page-description format back into linear, structured text with page provenance intact.

document parsing layout analysis reading order provenance

A PDF does not contain paragraphs. It contains a content stream: a sequence of drawing operators that place glyphs at coordinates on a canvas. “This character, this font, at x=72.4, y=531.2.” There is no inherent notion of a sentence, a column, a heading, or even a word — those are things a human reconstructs visually from spatial arrangement.

So extraction is inference, not decoding. A naive extractor walks the content stream in storage order and concatenates glyphs. On a single-column page that accidentally works. On a two-column academic paper — exactly what our test corpus is — storage order frequently interleaves the columns, producing text that alternates between two unrelated arguments mid-sentence.

A layout-aware extractor instead clusters glyphs into lines, lines into blocks, detects column boundaries geometrically, then emits blocks in human reading order. It also infers structure from typography: larger and bolder becomes a Markdown heading, a repeating x-offset becomes a list, a grid of aligned cells becomes a table.

The difference between a transcriber who types what they see left-to-right across a newspaper — mixing two stories into nonsense — and one who recognizes the column rule and follows each story down before moving right.

Mechanism · src/ingest.py
def extract_pages(pdf_path) -> list[tuple[int, str]]:
    # page_chunks=True returns one dict per page rather than
    # one concatenated string, which is what preserves provenance.
    pages = pymupdf4llm.to_markdown(str(pdf_path), page_chunks=True)
    return [(i + 1, p["text"]) for i, p in enumerate(pages)]

# -> [(1, "# Attention Is All You Need\n\n..."), (2, "..."), ...]
#      ^ 1-indexed to match what a human sees in a PDF reader
Why the page number is captured here and nowhere else Page identity exists at parse time and is destroyed by every later step — chunking splits text, embedding discards text entirely. If the page number is not attached to each unit of text at this exact moment, no downstream step can recover it, and the citation requirement becomes unimplementable. Capturing provenance at the earliest possible stage is the single design decision that makes [source, page N] possible.
Step 02

Chunking — a sliding window with stride

Splitting each page into overlapping fixed-size windows, each independently retrievable.

chunking fixed-size windowing stride chunk_overlap boundary loss

Retrieval operates on units. Too large a unit and a match returns mostly irrelevant text, diluting the signal sent to the model; too small and the unit loses the context that made it meaningful. Fixed-size windowing is the simplest workable policy: walk the page in windows of size, advancing by a stride of size − overlap each time.

The unit of size matters more than it appears. Our first implementation measured in words, which felt natural but was the wrong axis — the encoder's input limit is denominated in tokens, and the ratio between them is neither fixed nor small. On this corpus a 500-word window averaged over 600 tokens. Sizing in the wrong unit produced the defect documented in step 3, so chunking is now driven by the encoder's own tokenizer.

One wrinkle: converting tokens back to text is lossy, because sub-word pieces do not reassemble into the original string exactly. So the windows are computed over tokens but cut from the source string using each token's character offsets. The stored chunk is byte-identical to the parsed Markdown, Unicode and formatting intact.

stride = size − overlap = 240 − 40 = 200 tokens
windowi = text[ offset(200·i)start : offset(200·i + 240)end ] 240 leaves headroom under the encoder's 256-token ceiling for the [CLS] and [SEP] tokens added at encode time — measured maximum is 242.
Mechanism · src/ingest.py
def chunk_text(text, tokenizer, size, overlap):
    # offset_mapping gives (char_start, char_end) per token, which is what
    # lets us cut on token counts without detokenizing.
    enc = tokenizer(text, add_special_tokens=False, return_offsets_mapping=True)
    offsets = enc["offset_mapping"]

    chunks, start = [], 0
    while start < len(offsets):
        window = offsets[start : start + size]
        piece  = text[window[0][0] : window[-1][1]].strip()   # slice the ORIGINAL string
        if piece:
            chunks.append(piece)
        if start + size >= len(offsets):
            break                          # avoid a tail already inside the last window
        start += size - overlap             # advance by the stride
    return chunks

# Chunking is applied PER PAGE, not to the whole document:
for page_num, page_text in extract_pages(pdf_path):
    for piece in chunk_text(page_text, tokenizer, 240, 40):
        chunks.append({"source": name, "page": page_num, "text": piece})
The page-boundary tradeoff Because chunking runs inside the per-page loop, no chunk can ever span two pages — which is precisely what keeps page a single unambiguous integer per chunk. The cost is real: a paragraph flowing across a page break is cut at the break with no overlap to rescue it. We accepted unambiguous citations over perfect continuity. It also explains the shape of the corpus — 15 pages yielded 64 chunks, and the shortest is only 44 tokens, the tail end of a sparse page.
Step 03

Embedding — projecting text into a metric space

A neural encoder maps variable-length text to a fixed 384-dimensional vector where geometric proximity approximates semantic similarity.

embedding bi-encoder mean pooling dense vector L2 normalization max_seq_length

The embedding model is a small transformer — six layers, trained specifically so that texts with similar meaning land near each other. The forward pass is mechanical:

1. Tokenize. Text is split into sub-word tokens by a WordPiece vocabulary. Not words — tokens. This distinction matters enormously in a moment. Technical prose tokenizes badly: rare terms fragment into several pieces each.

2. Encode. Each token becomes a 384-dim vector, and six layers of self-attention let every token's representation absorb context from every other token. This is why the model can tell that “bank” near “river” differs from “bank” near “deposit”.

3. Pool. The result is one vector per token, but we need one vector per chunk — so the token vectors are averaged element-wise (mean pooling) into a single 384-dim vector.

4. Normalize. Each vector is scaled to unit length. This discards magnitude and keeps only direction — and direction is where meaning lives.

The model places every chunk as a point on the surface of a 384-dimensional sphere. Two chunks about the same idea sit close together on that surface even when they share no vocabulary at all; “revenue increased” and “sales grew” are near neighbours despite zero overlapping words.

Defect found by measurement — since fixed

Most of each chunk was invisible to search

all-MiniLM-L6-v2 has a hard input ceiling of max_seq_length = 256 tokens. Anything past token 256 is silently truncated before the encoder ever sees it — no exception, no warning at encode time. The failure is invisible unless you go looking.

The original chunk size was specified in words (500) while the limit is in tokens. Measured across the real corpus: median chunk 626 tokens, largest 1,212, with 15 of 22 chunks over the ceiling and losing a median of 370 tokens each.

The consequence is subtle and worth stating precisely: the dropped text was still stored, still retrievable, and still sent to the model once its chunk was selected — so no answer was ever wrong because of it. But that text could not contribute to its own chunk's vector, meaning it could never influence whether that chunk got selected at all. Roughly 60% of the corpus was unfindable but not unusable.

Fixed by windowing on tokenizer offsets instead of whitespace (step 2), plus an assertion in ingest.py that refuses to build an index if any chunk exceeds the ceiling — so the failure cannot recur silently.

Step 04

Indexing — the vector store and its sidecar

Persisting vectors for fast nearest-neighbour search, and the alignment invariant that keeps text and page numbers attached to them.

vector store IndexFlatIP inner product cosine similarity exact vs. ANN parallel arrays

FAISS stores an n × d matrix of float32 and answers one question fast: given a query vector, which stored rows are closest? Two design choices define our index.

Exact, not approximate. IndexFlatIP is brute force — it compares the query against every single stored vector. At 22 vectors that is 8,448 multiply-accumulate operations, which is nothing. Approximate indexes (HNSW, IVF) trade a little recall for sub-linear search and only start paying off in the hundreds of thousands of vectors. Choosing exact search now means retrieval quality problems are unambiguously our problems, never the index quietly missing a true neighbour.

Inner product on normalized vectors. The IP suffix means the scoring function is the dot product. Because step 3 normalized everything to unit length, that dot product is cosine similarity.

cos(θ) = (u · v) / (‖u‖ ‖v‖)   →   when ‖u‖ = ‖v‖ = 1   →   cos(θ) = u · v Scores run −1 to 1. Our observed top-5 for “What is multi-head attention?” ranged 0.634 down to 0.402.
Mechanism · src/ingest.py
dim   = embeddings.shape[1]        # 384
index = faiss.IndexFlatIP(dim)      # Flat = exhaustive, IP = inner product
index.add(embeddings.astype(np.float32))

faiss.write_index(index, STORE_DIR / "index.faiss")
json.dump(all_chunks, open(STORE_DIR / "metadata.json", "w"))
#         ^ same list, same order --- this is the invariant
The fragile part of the design Nothing in the code enforces that the two files stay aligned — it holds only because both are written from the same list in the same order, in the same function, in one pass. Any future change that filters, sorts, deduplicates, or incrementally appends to one without the other silently corrupts every citation the system produces: the answer text would be right while the page number points somewhere else. A production version stores an explicit id on each record instead of relying on positional coincidence.
Step 05

Retrieval — symmetric encoding and top-k

Projecting the question into the same space as the corpus, then taking the k nearest rows.

retrieval semantic search top-k query embedding recall@k

The critical constraint is symmetry: the query must be encoded by the identical model, with the identical normalization, as the corpus was. A vector produced by a different model occupies a different space, and distances between the two are arithmetically computable but semantically meaningless — the system would return confident nonsense.

Search itself is one matrix multiplication: the (1, 384) query against the transposed (22, 384) corpus gives 22 scores, from which FAISS returns the k highest along with their row ids. Those ids are then resolved against the metadata sidecar to recover text, source, and page.

Mechanism · src/retrieve.py
query_vec = model.encode([query], convert_to_numpy=True)   # (1, 384)
faiss.normalize_L2(query_vec)                             # same treatment as corpus

scores, ids = index.search(query_vec.astype(np.float32), k)

for score, idx in zip(scores[0], ids[0]):
    if idx == -1:                # FAISS pads with -1 when k > ntotal
        continue
    chunk = metadata[idx]        # <-- the invariant being cashed in
    results.append({**chunk, "score": float(score)})

Open limitation — structural, not a bug

Vector similarity measures aboutness, not answerhood

Fixing truncation did not move ranks 1 and 2, and that is the informative part. Those figure captions repeat “attention heads” several times inside a very short chunk, giving them high topical density; the actual definition is longer and more discursive, so averaging its tokens into one vector dilutes the signal. A short on-topic fragment out-scores a long precise one — and no amount of re-chunking changes that, because it is inherent to compressing a passage into a single point.

Recall is good — the right passage is reliably inside the top 5, so the model does receive it and can still answer correctly. Precision@1 is the weak spot. That distinction matters: it means the system is usable today but wastes context on near-misses, and would degrade if k were tightened.

This is precisely the gap a cross-encoder reranker closes, and it is now the best-evidenced reason to build one: retrieve k=20 cheaply with the bi-encoder, then re-score each candidate by encoding query and chunk together — letting the two texts attend to each other rather than comparing pre-computed summaries — and keep the best 5. That is the first task of Phase 2.

Step 06

Generation — constrained synthesis with attribution

Assembling retrieved context into a prompt that permits only grounded, cited claims.

generation context window system prompt citation grounding closed-book vs. open-book abstention

Everything up to here was search. This step is the “augmented generation” half of RAG: the model is converted from a closed-book system answering out of parametric memory into an open-book one answering out of supplied evidence.

Three things are enforced in the prompt. Restriction — answer only from the provided excerpts. Attribution — emit [source, page N] for every claim, which is trivially satisfiable because each excerpt is labelled with its provenance in the context itself. Abstention — say so plainly when the context does not contain the answer. Abstention is the one that most reduces hallucination: without an explicit licence to decline, a model under instruction to answer will tend to produce something.

Mechanism · src/generate.py · what goes over the wire
# Each retrieved chunk is rendered with its provenance inline,
# so the citation the model must emit is already in front of it.
context = "\n\n---\n\n".join(
    f"[{c['source']}, page {c['page']}]\n{c['text']}" for c in chunks
)

client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    output_config={"effort": "low"},        # extraction, not deep reasoning
    system=SYSTEM_PROMPT,                    # restriction + attribution + abstention
    messages=[{"role": "user",
               "content": f"Context:\n\n{context}\n\nQuestion: {query}"}],
)

The difference between asking a well-read colleague to answer from memory, and handing them five marked-up photocopies with the page numbers written in the margin, saying: answer using only these, cite which one, and tell me if the answer isn't in here.

Separation of concerns worth noticing The model is never asked to find anything — retrieval already did that, deterministically and cheaply. It is asked only to read, synthesise, and attribute. That split is what makes the system auditable: when an answer is wrong you can inspect the retrieved set and immediately tell whether retrieval failed to surface the evidence, or generation mishandled evidence it was given. Those are different bugs with different fixes.

Glossary

chunk
One independently retrievable unit of text, plus the metadata identifying where it came from.
embedding / dense vector
A fixed-length array of floats encoding a text's meaning as a position in a metric space. Here, 384 float32 values.
bi-encoder
An architecture that encodes query and document separately, so document vectors can be precomputed. Fast, but it never lets the two texts interact.
cross-encoder
Encodes query and document together for a far more accurate relevance score. Too slow to run over a whole corpus — hence its use as a second-stage reranker.
mean pooling
Averaging per-token vectors into one per-chunk vector. Cheap and effective, but it dilutes long passages.
cosine similarity
The cosine of the angle between two vectors; on unit-length vectors it equals their dot product. Range −1 to 1.
max_seq_length
The token ceiling of an encoder. Input beyond it is silently truncated — the source of the defect documented in step 3.
top-k / recall@k
Returning the k highest-scoring chunks; recall@k asks whether the correct chunk appears anywhere in that set.
exact vs. approximate (ANN)
Exact search compares every vector and is always right; ANN structures trade a little recall for sub-linear speed at scale.
citation grounding
Constraining the model to answer only from supplied context and cite its provenance — the primary hallucination control in RAG.
abstention
Explicitly licensing the model to say “not in the provided context” rather than inventing an answer.
closed-book vs. open-book
Answering from parametric memory versus from evidence supplied at inference time. RAG converts the former into the latter.

What Phase 1 left broken

One measured failure, and the structural reason no amount of re-chunking could fix it.

Phase 1 ended with retrieval that worked but ranked badly. Asked “What is multi-head attention?”, it returned a figure caption from page 14 at rank 1 and the actual definition at rank 4. Fixing the truncation defect improved the tail of the results and moved nothing at the top — ranks 1 and 2 came back byte-identical, at identical scores.

That non-result was the useful one. It ruled out the explanation I expected and left only the structural one: a bi-encoder scores topical aboutness, not answerhood. Mean pooling compresses a whole passage into one 384-dimensional point, so a short caption repeating “attention heads” three times reads as densely on-topic, while a longer passage that actually defines the term gets diluted by its own surrounding prose. No chunking parameter reaches that; it is inherent to summarising a passage into a single vector before the query is known.

Phase 2 is three changes and one discipline. Rerank the shortlist with a model that reads query and passage together. Add a lexical retriever to cover the dense retriever's blind spot. Fuse the two rankings. And — the discipline — measure all of it, because the previous paragraph is a plausible story and plausible stories are how retrieval systems quietly get worse.

Step 07

Reranking — letting the query and the passage meet

A second-stage model that encodes question and candidate jointly, rather than comparing two summaries written in isolation.

cross-encoder bi-encoder two-stage retrieval joint encoding precision@1

The bi-encoder from Phase 1 has a property that makes it fast and, in the same stroke, imprecise: it encodes the query and the chunk separately. Chunk vectors are computed once at index time, long before any question exists, so at query time the comparison is between two independently-written summaries. The chunk was never allowed to know what was being asked of it.

A cross-encoder removes exactly that constraint. Query and chunk are concatenated into one sequence and passed through the encoder together, so every query token can attend to every chunk token and vice versa. The model isn't asked “summarise this passage” and then compared — it is asked the only question that matters: does this passage answer this query?

The cost is that nothing can be precomputed. Every (query, chunk) pair needs its own forward pass, so scoring a 64-chunk corpus means 64 forward passes and a million-chunk corpus is out of the question. That is why this is a second stage: the bi-encoder scans everything cheaply to produce a shortlist, and the cross-encoder spends real computation only on the survivors.

In your project cross-encoder/ms-marco-MiniLM-L-6-v2, run over the top 20 candidates and cutting to 5. It outputs raw logits, not similarities: ordering is meaningful, the absolute values are not comparable to cosine scores, and they can be negative. The first-stage score is preserved on each result as retrieval_score so the two stages remain separable.

Step 08

Sparse retrieval — covering the dense blind spot

BM25 scores exact term overlap weighted by rarity, which is precisely what embeddings smooth away.

BM25 sparse retrieval lexical matching IDF term saturation

Embeddings are strong on paraphrase because they map meaning to geometry. That same mechanism is a weakness for tokens whose value is their identity rather than their semantics: P100, WMT 2014, d_model, BLEU. A rare symbol contributes a small nudge to a 384-dimensional average dominated by the surrounding prose, so a query naming it exactly gets little extra pull toward the chunk that contains it.

BM25 has the mirror-image profile. It scores documents by term overlap, weighting each shared term by inverse document frequency — a term occurring in few chunks is treated as far more informative than one occurring everywhere. A rare token is therefore the strongest possible signal, which is exactly backwards from the dense retriever. It also applies term saturation: the fifth occurrence of a word adds much less than the second, so keyword-stuffed passages cannot run away with the score.

Its blind spot is the dense retriever's strength: BM25 cannot see paraphrase at all. A query saying “how fast does it train” shares no terms with a passage saying “step time was 1.0 seconds” and scores exactly zero. Neither retriever is better; they fail on disjoint inputs, which is the entire argument for running both.

Mechanism · src/hybrid.py
# Deliberately crude tokenization: no stemming, no stopword list.
# Stemming would collapse distinctions this corpus depends on
# (d_k vs d_v), and IDF already discounts common words without
# needing a stoplist.
TOKEN_RE = re.compile(r"[a-z0-9]+")

def build_bm25(metadata):
    return BM25Okapi([tokenize(c["text"]) for c in metadata])

def bm25_search(query, bm25, metadata, k):
    scores = bm25.get_scores(tokenize(query))
    ranked = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)[:k]
    return [{**metadata[i], "chunk_id": i, "score": float(scores[i])}
            for i in ranked if scores[i] > 0]   # 0 = no query term present
Step 09

Fusion — combining two incomparable rankings

Cosine similarities and BM25 scores live on unrelated scales, so the safe way to merge them is to ignore the scores entirely.

reciprocal rank fusion score normalization rank fusion

Merging the two result lists sounds like addition, but a cosine similarity of 0.63 and a BM25 score of 11.4 are not commensurable quantities — one is bounded in [−1, 1], the other is unbounded and depends on corpus statistics. Adding them directly is meaningless, so any weighted approach must first normalize each list, usually min-max, per query.

That normalization introduces its own distortion: it is relative. A query where every candidate is mediocre still produces a top score of 1.0 after scaling, identical to a query with a perfect match. The normalized number says where a result stands among its peers, not whether it is any good — and it silently erases the confidence signal.

Reciprocal rank fusion avoids the problem by discarding scores and using only positions. Each retriever contributes 1 / (k + rank) per document, and the contributions are summed. Being ranked highly by both retrievers beats being ranked first by one, the arithmetic is scale-free by construction, and there is no weight to tune per corpus.

RRF(d) = Σr ∈ retrievers 1 / (k + rankr(d))     k = 60 The constant damps the difference between top ranks, so rank 1 versus rank 2 is not treated as a decisive gap — a hedge against either retriever being overconfident.
Why RRF is the default here Weighted fusion measured comparably (see the results below) but carries an alpha that needs retuning per corpus, and inherits the normalization distortion above. RRF wins on robustness rather than on the numbers — it has one fewer thing to get wrong when the corpus changes.
Step 10

Evaluation — the part that makes the rest trustworthy

Three metrics, a labelled golden set, and a deliberate separation between what each pipeline stage is responsible for.

golden set hit rate MRR NDCG recall vs precision

Everything above is a plausible argument. Plausible arguments are how retrieval systems quietly degrade — each change sounds sensible, nobody measures, and six changes later quality has drifted with no way to identify which one did it. So the third piece of Phase 2 is a harness that scores any configuration against 24 labelled questions plus 4 deliberately unanswerable ones.

The three metrics, and what each one hides

MetricAsksBlind to
hit rate@k Is a relevant chunk anywhere in the returned set? Position. Rank 1 and rank 5 score identically — so it saturates at 1.000 and stops being informative.
MRR How high is the first relevant result? (1/rank) Everything after the first hit. A set with one perfect result scores the same as one with five.
NDCG@k Are all relevant results near the top, discounted by rank? Absolute quality — it is normalized against the best achievable ordering of what was actually retrieved.
Why relevance is labelled per page, not per chunk A chunk counts as relevant if it came from a page the golden set lists. This is coarse — it cannot distinguish a precise passage from a vague one on the same page. It was chosen because page labels survive re-chunking: chunk-level labels would need redoing after every change to chunk size, which is exactly when a comparable metric matters most. Labelling at a granularity that changes with your parameters means never being able to compare across the change you most want to evaluate.
Bug caught by the harness, in its own first run

NDCG returned values above 1.0

NDCG is normalized and cannot exceed 1.0, so the first run printing 1.373 was proof of a defect in the metric itself, not a good result.

The cause was the page-level labelling above: several returned chunks can share one gold page, so the achieved DCG summed over all of them while my ideal DCG allowed only one slot per gold page. The ideal is now defined as the hits actually found, moved to the top, which is the standard formulation for binary relevance with an unknown total. Verified against four hand-computed cases — all-hits-at-top returning exactly 1.0, hits demoted returning 0.571, no hits returning 0.0.

Worth stating plainly: this bug was in the tool built to catch bugs, and it was caught only because the output violated a bound I knew the metric had. A metric with no known bounds would have shipped wrong.

The measurement that changed a default

Hybrid search looked useless — because the corpus is small

Read only from the table above, fusion does nothing: identical hit@5 and MRR to dense-only. That reading is wrong, and the reason matters more than the number.

On a 64-chunk corpus, a 20-candidate pool is 31% of the entire corpus. Recall is trivially perfect for any first stage, so fusion has no headroom to fill — and while it does improve pool ordering (candidate MRR 0.774 → 0.883), the reranker re-scores every candidate from scratch and discards that ordering entirely. Both effects cancel.

Sweeping candidate depth puts the pool into the selectivity regime a corpus of hundreds of documents would actually operate in:

Abstention — an unplanned finding

The four adversarial cases have no correct answer anywhere in the corpus. A good system should be visibly less confident about them. Top-1 score on each:

StageScores on the four unanswerable questions
dense first stage (cosine)+0.43, +0.34, +0.35, +0.27
after reranking (logits)−7.04, +0.96, −8.13, −9.90

Cosine similarity cannot separate answerable from unanswerable — those scores sit in the same band as genuine matches, because something in a 64-chunk corpus is always the nearest neighbour. Cross-encoder logits separate three of four decisively, which makes a negative rerank score a usable abstention threshold. The survivor scores +0.96 for a defensible reason: the question asks what the model cost in dollars, and the paper genuinely does discuss training cost — in FLOPs. That is a near-miss, not a failure of the signal.

This was not something we set out to build. It arrived as a side effect of adding adversarial cases to the golden set, and it supplies most of the checklist's “fallback when confidence is low” item for free.

How much to trust these numbers

24 cases is small. Each case is worth roughly 4 points of hit rate, so a single case flipping moves the metric visibly. Treat differences under ~0.05 as noise, and the gaps between the three reranked configurations are all inside that band.

One document. Nothing here tests cross-document retrieval, where returning the right passage from the wrong document is a distinct failure mode that cannot occur in a single-source corpus.

Page-level relevance is coarse. It cannot tell a precise passage from a vague one on the same page, so it systematically over-credits a chunk that merely shares a page with the answer.

The labels were drafted by the same process that built the system, then spot-checked rather than independently authored. That is a real weakness in the methodology and the reason the golden set deliberately includes cases expected to fail.

Most importantly: the candidate-depth sweep demonstrated that a conclusion drawn from this corpus can invert at realistic scale. Treat every number here as measured on 64 chunks of one paper, and re-measure before trusting any of it on a real corpus.

What Phase 2 left slow — and invisible

Two problems that are really the same problem: the system did work nobody could see, and repeated work nobody needed.

Phase 2 made retrieval good. It did not make it usable, and it left the thing entirely opaque. Two symptoms, measured:

Re-indexing cost 432 seconds every time. Adding one document to twenty meant re-reading, re-splitting and re-encoding all twenty-one from scratch. Since the corpus is meant to grow document by document, that cost lands on every single addition — the operation you do most often was the most expensive one.

And you could not see why it returned anything. Ask a question, get five passages. Everything that produced them — which of the two retrievers found what, how their disagreement was resolved, what the reranker promoted or buried, what the diversity cap threw out — was computed and then thrown away. Fine for serving. Useless for understanding, and understanding was the entire point of building this by hand.

Phase 3 is caching, profiling, and a user interface whose actual job is to make the invisible part visible.

Step 12

Caching — addressing work by its content, not its name

Three layers of remembered work, each keyed on a fingerprint of the input rather than a filename or a timestamp.

content-addressed hash cache key invalidation salt

A cache is stored work you can reuse instead of redoing. The whole difficulty is knowing when the stored copy has gone stale — the industry joke that cache invalidation is one of the two hard problems in computing is a joke because it is true, and because the failure is silent. A cache that returns the wrong answer is far worse than no cache at all: you get a confidently incorrect result with no error to alert you.

The usual approach keys on the filename and the modification date. Both lie. Sync clients — Google Drive and OneDrive especially — touch modification times constantly without changing a byte, and renaming a file changes its name while changing nothing about its contents.

So each cache here is content-addressed: the key is a hash of the file's actual bytes. A hash is a fixed-length fingerprint — change one character anywhere in a 60-page document and the fingerprint changes completely. That gives three properties for free:

Filing by a photograph of the contents rather than by the label on the folder. Retitle the folder, move it to another cabinet, or put it back untouched after a year — the photograph still matches. Change a single line inside, and it no longer does.

SituationKeyed on name + timestampKeyed on content hash
File renamed or movedFull re-parse — wastedRecognised, reused
Sync client touches the fileFull re-parse — wastedRecognised, reused
File genuinely editedRe-parsedRe-parsed, with no staleness window
Two copies, different namesBoth parsedParsed once

Three layers accumulated over the project, each removing the bottleneck that the previous one exposed. Removing the embedding cost revealed parsing as the new ceiling; removing parsing revealed chunking and the safety check behind it.

LayerStoresKey includesRemoved
embedding_cache.py The 384-number vector for each chunk chunk text + model name ~6 min of encoding
parse_cache.py Text recovered from each document file bytes + parser version 300 s of 432 s
parse_cache.py (chunk layer) Finished chunks, report and verdict file bytes + parser version + chunk settings The remaining 43 %

The third column is where the real care went. A key must include everything that changes the output, not just the input file. The chunk cache stores text that was split using a particular chunk size and overlap — so those settings are mixed into the key as a salt, an extra ingredient that changes the fingerprint. Without it, changing the chunk size would appear to do nothing: the system would keep serving chunks built under the old setting, and you would conclude the parameter did not matter. The same reasoning puts a PARSER_VERSION number in the parse key, so that improving a loader actually invalidates the documents it affects.

Mechanism · src/parse_cache.py
def file_key(path, salt="") -> str:
    digest = hashlib.sha256()
    # Read in 1 MB blocks so a 200 MB scan does not land in memory at once.
    with open(path, "rb") as fh:
        for block in iter(lambda: fh.read(1 << 20), b""):
            digest.update(block)
    # Everything else that changes the derived output for identical bytes.
    digest.update(f"\x00v{PARSER_VERSION}\x00{salt}".encode())
    return digest.hexdigest()[:32]

# chunk_salt() == "210-40-0"  -- size, overlap, title-prefix flag

One more decision worth naming, because it is the opposite of the instinct: when the cache looks damaged — a truncated file, a key count that disagrees with the vector count — it is discarded rather than repaired. Rebuilding is merely slow. A half-trusted cache silently returns another chunk's vector, and distances to a wrong vector are perfectly computable and completely meaningless.

Step 13

Profiling — when the measurement refutes the task

The requested optimisation targeted 0.1 % of the runtime. Measuring first is what caught it.

profiling bottleneck incremental indexing Amdahl's law

Profiling means timing each part of a program to find where the time actually goes, rather than where you assume it goes. The task on the list was “incremental indexing” — which in normal usage means updating the search index in place when a document is added, instead of rebuilding it. A sensible, standard optimisation.

The profile said rebuilding the index takes ten milliseconds.

This is Amdahl's law in its most practical form: the most you can possibly gain from speeding up one part is bounded by how much of the total that part occupies. Make index-building infinitely fast — instantaneous, free — and the run goes from 8.5 seconds to 8.49 seconds. The work would have been correct, well-engineered, and worth nothing.

So the profile changed the task. Instead of incremental index updates, three changes aimed at where the time actually was:

  1. Cache finished chunks, not just parsed text — removing the 24 % spent re-splitting documents that had not changed.
  2. Run the safety check only on new chunks. The token-budget guard re-verified every chunk on every run; cached chunks passed the identical check under identical settings when they were built, which the salt in the key guarantees. That is 19 % spent re-deriving a known answer.
  3. Load the model only if something needs it — the 48 %, covered next.
Step 14

Lazy loading — not paying for what you never use

The single largest cost was a model loaded out of habit, for a run that never touched it.

lazy loading deferred import import side effect wall-clock time

Lazy loading means deferring expensive setup until the moment something genuinely needs it — and skipping it entirely if that moment never arrives. The embedding model was loaded at the top of every run because usually it is needed. On a fully-cached re-index it is needed for exactly nothing: no chunk is built, so no tokenizer is consulted, and no text is encoded. Four seconds, every run, for a model that was never asked a question.

Wrapping it in a handle that loads on first genuine use removed that. It also exposed a bug I had written myself, which is the honest part of the story: the code passed lazy.get() into the embedding step, and .get() is what forces the load. The optimisation was silently doing nothing. The fix was to pass the unopened handle and let the cache decide — it only resolves the model if there are chunks it does not already have.

Mechanism · src/embedding_cache.py
    _, misses = cache.get_many(texts, model_name)

    if misses:
        # Resolved only here: `model` may be a lazy handle, and when every
        # text is already cached the model is never needed at all.
        model = model.get() if hasattr(model, "get") else model
        fresh = model.encode(missing_texts, convert_to_numpy=True)

That took the measured section from 8.5 s to 0.3 s — but the command still took 22 seconds to finish. The gap is the difference between the time your program measures and wall-clock time, the time you actually wait. The remainder was Python loading the machine-learning libraries themselves, before a single line of my code ran. In Python, importing a library executes it, and sentence_transformers pulls in PyTorch — hundreds of megabytes of numerical machinery — as an import side effect.

Moving that import inside the lazy handle, so it only happens when the model is truly needed, took the wall clock from 22 s to 0.76 s.

ScenarioBeforeAfterWhat happens

Re-index, nothing changed432 s0.76 s All four layers hit; model never loaded

The middle row is the one that matters day to day, and the third is the one the corpus will actually live on. Note that the first row does not improve at all — caching never makes new work faster, it only stops old work from being repeated. Claiming otherwise would be the kind of number that looks good in a summary and misleads anyone who relies on it.

Step 15

The Retrieval Inspector — making the pipeline legible

Five stages each reorder the results. Until now, four of those orderings were computed and discarded.

instrumentation glass box bump chart observability

Instrumentation is adding the ability to observe a system's internal state while it runs. The retrieval pipeline had none: it produced five passages and silently dropped every intermediate ranking that led there. So pipeline_trace.py re-runs the same stages while keeping all of it — which retriever found what, how the two disagreeing rankings were reconciled, what the reranker promoted or buried, what the diversity cap displaced, and where the final score landed relative to the refusal threshold.

The centrepiece of the interface is a bump chart: a diagram where vertical position is rank and each line is one passage travelling left to right through the pipeline. Lines that climb steeply are the pipeline earning its keep.

One design decision is worth spelling out, because it is a habit rather than a trick. The tracer does not modify the serving code. A serving path that carries debug state is a serving path that eventually ships debug state, and the two want opposite things: one should be fast and forget everything, the other slow and remember everything.

The price of that separation is duplication — the stage order exists in two places and could drift apart. So a test asserts that the tracer and the real pipeline return byte-identical results, verified across four queries including one the system is supposed to refuse. That test is what makes the duplication safe to keep rather than a bug waiting to happen.

Caught before it could bite

A module named trace would have shadowed Python's own

The file was first written as src/trace.py. Python has a built-in module called trace, and because src/ is searched first, every library in the project asking for the standard one would silently have received mine instead — a failure that surfaces far from its cause, in someone else's code. Renamed to pipeline_trace.py.

The interface immediately earned its place by exposing a defect rather than hiding one. Asked how normalisation statistics are computed across features rather than examples, the system still ranks Batch Normalization first — which is the concept the phrase “rather than examples” explicitly rules out. That is the known cross-document confusion from Phase 2, no longer a paragraph in a results file but a visible line on a chart.

Why build this when NotebookLM exists

The honest answer is not “better answers”, and pretending otherwise would be the weaker position.

A hand-built system will not beat Google's NotebookLM or an enterprise product like Glean on raw answer quality. They have better underlying models, far more compute, and teams working on nothing else. Competing there means losing on their terms.

But both share a structural weakness, and it is not an oversight — it follows from being a polished consumer product. They are closed systems that always sound confident. You cannot see why a passage was chosen, cannot measure whether a change helped, and are never told the system is unsure. That is defensible ground precisely because they cannot concede it without becoming a different kind of product.

Question a user actually hasClosed productThis system

There is a second reason, and for a project whose stated purpose is learning it is the stronger one. A system you assembled from parts is a system whose failures you can diagnose. Every number in these notes was produced by a measurement you can re-run, and four separate times a measurement overturned a decision that sounded obviously right. That is not an experience a finished product can give you, because a finished product's whole job is to prevent it.

What Phase 3 leaves open

Stated plainly, because a status document that only lists wins is not a status document.

The corpus is twenty PDFs and nothing else. Loaders for Word, PowerPoint, Excel and scanned documents are written and have never run on real files. The spreadsheet path is the least trustworthy: rows are serialised into Column: value text on the assumption that this retrieves well, and that assumption has no evidence behind it. This is the largest unknown in the system and the cheapest to resolve.

Cross-document confusion is still unsolved at roughly 15 % of questions. The mechanism is understood — the retriever matches the topic and ignores the constraint that distinguishes the answer — and the obvious fix has been ruled out by measurement. The real fix is decomposing the query before retrieving, which needs a language model.

Generation is unverified end to end. Retrieval-only was a deliberate choice — it cannot hallucinate and costs nothing — but the path that writes prose with inline citations has never completed a real call, because the account has no credit. The code is written; the evidence is not.

Indexing progress is emitted but unread. build_index() already reports structured events for every stage; nothing displays them yet.
