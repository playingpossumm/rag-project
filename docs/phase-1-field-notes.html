Anatomy of a Retrieval Pipeline

A step-by-step account of what actually happens to a PDF as it becomes searchable, and to a question as it becomes a cited answer. This is the Retrieval-Augmented Generation (RAG) pattern: retrieve first, then generate strictly from what was retrieved. Every number below is measured from the running system, not estimated — including a silent truncation defect those measurements exposed, its fix, and the before-and-after that separates what the fix solved from what it did not.

Step 01

Parsing — recovering text from a print format

Turning a page-description format back into linear, structured text with page provenance intact.

document parsing layout analysis reading order provenance

A PDF does not contain paragraphs. It contains a content stream: a sequence of drawing operators that place glyphs at coordinates on a canvas. “This character, this font, at x=72.4, y=531.2.” There is no inherent notion of a sentence, a column, a heading, or even a word — those are things a human reconstructs visually from spatial arrangement.

So extraction is inference, not decoding. A naive extractor walks the content stream in storage order and concatenates glyphs. On a single-column page that accidentally works. On a two-column academic paper — exactly what our test corpus is — storage order frequently interleaves the columns, producing text that alternates between two unrelated arguments mid-sentence.

A layout-aware extractor instead clusters glyphs into lines, lines into blocks, detects column boundaries geometrically, then emits blocks in human reading order. It also infers structure from typography: larger and bolder becomes a Markdown heading, a repeating x-offset becomes a list, a grid of aligned cells becomes a table.

The difference between a transcriber who types what they see left-to-right across a newspaper — mixing two stories into nonsense — and one who recognizes the column rule and follows each story down before moving right.

Mechanism · src/ingest.py
def extract_pages(pdf_path) -> list[tuple[int, str]]:
    # page_chunks=True returns one dict per page rather than
    # one concatenated string, which is what preserves provenance.
    pages = pymupdf4llm.to_markdown(str(pdf_path), page_chunks=True)
    return [(i + 1, p["text"]) for i, p in enumerate(pages)]

# -> [(1, "# Attention Is All You Need\n\n..."), (2, "..."), ...]
#      ^ 1-indexed to match what a human sees in a PDF reader
Why the page number is captured here and nowhere else Page identity exists at parse time and is destroyed by every later step — chunking splits text, embedding discards text entirely. If the page number is not attached to each unit of text at this exact moment, no downstream step can recover it, and the citation requirement becomes unimplementable. Capturing provenance at the earliest possible stage is the single design decision that makes [source, page N] possible.
Step 02

Chunking — a sliding window with stride

Splitting each page into overlapping fixed-size windows, each independently retrievable.

chunking fixed-size windowing stride chunk_overlap boundary loss

Retrieval operates on units. Too large a unit and a match returns mostly irrelevant text, diluting the signal sent to the model; too small and the unit loses the context that made it meaningful. Fixed-size windowing is the simplest workable policy: walk the page in windows of size, advancing by a stride of size − overlap each time.

The unit of size matters more than it appears. Our first implementation measured in words, which felt natural but was the wrong axis — the encoder's input limit is denominated in tokens, and the ratio between them is neither fixed nor small. On this corpus a 500-word window averaged over 600 tokens. Sizing in the wrong unit produced the defect documented in step 3, so chunking is now driven by the encoder's own tokenizer.

One wrinkle: converting tokens back to text is lossy, because sub-word pieces do not reassemble into the original string exactly. So the windows are computed over tokens but cut from the source string using each token's character offsets. The stored chunk is byte-identical to the parsed Markdown, Unicode and formatting intact.

stride = size − overlap = 240 − 40 = 200 tokens
windowi = text[ offset(200·i)start : offset(200·i + 240)end ] 240 leaves headroom under the encoder's 256-token ceiling for the [CLS] and [SEP] tokens added at encode time — measured maximum is 242.
Mechanism · src/ingest.py
def chunk_text(text, tokenizer, size, overlap):
    # offset_mapping gives (char_start, char_end) per token, which is what
    # lets us cut on token counts without detokenizing.
    enc = tokenizer(text, add_special_tokens=False, return_offsets_mapping=True)
    offsets = enc["offset_mapping"]

    chunks, start = [], 0
    while start < len(offsets):
        window = offsets[start : start + size]
        piece  = text[window[0][0] : window[-1][1]].strip()   # slice the ORIGINAL string
        if piece:
            chunks.append(piece)
        if start + size >= len(offsets):
            break                          # avoid a tail already inside the last window
        start += size - overlap             # advance by the stride
    return chunks

# Chunking is applied PER PAGE, not to the whole document:
for page_num, page_text in extract_pages(pdf_path):
    for piece in chunk_text(page_text, tokenizer, 240, 40):
        chunks.append({"source": name, "page": page_num, "text": piece})
The page-boundary tradeoff Because chunking runs inside the per-page loop, no chunk can ever span two pages — which is precisely what keeps page a single unambiguous integer per chunk. The cost is real: a paragraph flowing across a page break is cut at the break with no overlap to rescue it. We accepted unambiguous citations over perfect continuity. It also explains the shape of the corpus — 15 pages yielded 64 chunks, and the shortest is only 44 tokens, the tail end of a sparse page.
Step 03

Embedding — projecting text into a metric space

A neural encoder maps variable-length text to a fixed 384-dimensional vector where geometric proximity approximates semantic similarity.

embedding bi-encoder mean pooling dense vector L2 normalization max_seq_length

The embedding model is a small transformer — six layers, trained specifically so that texts with similar meaning land near each other. The forward pass is mechanical:

1. Tokenize. Text is split into sub-word tokens by a WordPiece vocabulary. Not words — tokens. This distinction matters enormously in a moment. Technical prose tokenizes badly: rare terms fragment into several pieces each.

2. Encode. Each token becomes a 384-dim vector, and six layers of self-attention let every token's representation absorb context from every other token. This is why the model can tell that “bank” near “river” differs from “bank” near “deposit”.

3. Pool. The result is one vector per token, but we need one vector per chunk — so the token vectors are averaged element-wise (mean pooling) into a single 384-dim vector.

4. Normalize. Each vector is scaled to unit length. This discards magnitude and keeps only direction — and direction is where meaning lives.

The model places every chunk as a point on the surface of a 384-dimensional sphere. Two chunks about the same idea sit close together on that surface even when they share no vocabulary at all; “revenue increased” and “sales grew” are near neighbours despite zero overlapping words.

Defect found by measurement — since fixed

Most of each chunk was invisible to search

all-MiniLM-L6-v2 has a hard input ceiling of max_seq_length = 256 tokens. Anything past token 256 is silently truncated before the encoder ever sees it — no exception, no warning at encode time. The failure is invisible unless you go looking.

The original chunk size was specified in words (500) while the limit is in tokens. Measured across the real corpus: median chunk 626 tokens, largest 1,212, with 15 of 22 chunks over the ceiling and losing a median of 370 tokens each.

The consequence is subtle and worth stating precisely: the dropped text was still stored, still retrievable, and still sent to the model once its chunk was selected — so no answer was ever wrong because of it. But that text could not contribute to its own chunk's vector, meaning it could never influence whether that chunk got selected at all. Roughly 60% of the corpus was unfindable but not unusable.

Fixed by windowing on tokenizer offsets instead of whitespace (step 2), plus an assertion in ingest.py that refuses to build an index if any chunk exceeds the ceiling — so the failure cannot recur silently.

Why normalize Unit-length vectors are what make the next step cheap. Once ||u|| = ||v|| = 1, the cosine of the angle between two vectors is identical to their dot product — so a similarity search reduces to plain multiplication with no division and no square roots. The check confirms it: ||vector[0]|| = 1.000000.
Step 04

Indexing — the vector store and its sidecar

Persisting vectors for fast nearest-neighbour search, and the alignment invariant that keeps text and page numbers attached to them.

vector store IndexFlatIP inner product cosine similarity exact vs. ANN parallel arrays

FAISS stores an n × d matrix of float32 and answers one question fast: given a query vector, which stored rows are closest? Two design choices define our index.

Exact, not approximate. IndexFlatIP is brute force — it compares the query against every single stored vector. At 22 vectors that is 8,448 multiply-accumulate operations, which is nothing. Approximate indexes (HNSW, IVF) trade a little recall for sub-linear search and only start paying off in the hundreds of thousands of vectors. Choosing exact search now means retrieval quality problems are unambiguously our problems, never the index quietly missing a true neighbour.

Inner product on normalized vectors. The IP suffix means the scoring function is the dot product. Because step 3 normalized everything to unit length, that dot product is cosine similarity.

cos(θ) = (u · v) / (‖u‖ ‖v‖)   →   when ‖u‖ = ‖v‖ = 1   →   cos(θ) = u · v Scores run −1 to 1. Our observed top-5 for “What is multi-head attention?” ranged 0.634 down to 0.402.
Mechanism · src/ingest.py
dim   = embeddings.shape[1]        # 384
index = faiss.IndexFlatIP(dim)      # Flat = exhaustive, IP = inner product
index.add(embeddings.astype(np.float32))

faiss.write_index(index, STORE_DIR / "index.faiss")
json.dump(all_chunks, open(STORE_DIR / "metadata.json", "w"))
#         ^ same list, same order --- this is the invariant
The fragile part of the design Nothing in the code enforces that the two files stay aligned — it holds only because both are written from the same list in the same order, in the same function, in one pass. Any future change that filters, sorts, deduplicates, or incrementally appends to one without the other silently corrupts every citation the system produces: the answer text would be right while the page number points somewhere else. A production version stores an explicit id on each record instead of relying on positional coincidence.
Step 05

Retrieval — symmetric encoding and top-k

Projecting the question into the same space as the corpus, then taking the k nearest rows.

retrieval semantic search top-k query embedding recall@k

The critical constraint is symmetry: the query must be encoded by the identical model, with the identical normalization, as the corpus was. A vector produced by a different model occupies a different space, and distances between the two are arithmetically computable but semantically meaningless — the system would return confident nonsense.

Search itself is one matrix multiplication: the (1, 384) query against the transposed (22, 384) corpus gives 22 scores, from which FAISS returns the k highest along with their row ids. Those ids are then resolved against the metadata sidecar to recover text, source, and page.

Mechanism · src/retrieve.py
query_vec = model.encode([query], convert_to_numpy=True)   # (1, 384)
faiss.normalize_L2(query_vec)                             # same treatment as corpus

scores, ids = index.search(query_vec.astype(np.float32), k)

for score, idx in zip(scores[0], ids[0]):
    if idx == -1:                # FAISS pads with -1 when k > ntotal
        continue
    chunk = metadata[idx]        # <-- the invariant being cashed in
    results.append({**chunk, "score": float(score)})

Everything below them improved: the page-5 definition rose 0.506 → 0.537, a second substantive page-5 chunk entered the set, and page 3's definition of the attention function displaced a section-heading chunk that carried no real content. Open limitation — structural, not a bug

Vector similarity measures aboutness, not answerhood

Fixing truncation did not move ranks 1 and 2, and that is the informative part. Those figure captions repeat “attention heads” several times inside a very short chunk, giving them high topical density; the actual definition is longer and more discursive, so averaging its tokens into one vector dilutes the signal. A short on-topic fragment out-scores a long precise one — and no amount of re-chunking changes that, because it is inherent to compressing a passage into a single point.

Recall is good — the right passage is reliably inside the top 5, so the model does receive it and can still answer correctly. Precision@1 is the weak spot. That distinction matters: it means the system is usable today but wastes context on near-misses, and would degrade if k were tightened.

This is precisely the gap a cross-encoder reranker closes, and it is now the best-evidenced reason to build one: retrieve k=20 cheaply with the bi-encoder, then re-score each candidate by encoding query and chunk together — letting the two texts attend to each other rather than comparing pre-computed summaries — and keep the best 5. That is the first task of Phase 2.

Step 06

Generation — constrained synthesis with attribution

Assembling retrieved context into a prompt that permits only grounded, cited claims.

generation context window system prompt citation grounding closed-book vs. open-book abstention

Everything up to here was search. This step is the “augmented generation” half of RAG: the model is converted from a closed-book system answering out of parametric memory into an open-book one answering out of supplied evidence.

Three things are enforced in the prompt. Restriction — answer only from the provided excerpts. Attribution — emit [source, page N] for every claim, which is trivially satisfiable because each excerpt is labelled with its provenance in the context itself. Abstention — say so plainly when the context does not contain the answer. Abstention is the one that most reduces hallucination: without an explicit licence to decline, a model under instruction to answer will tend to produce something.

Mechanism · src/generate.py · what goes over the wire
# Each retrieved chunk is rendered with its provenance inline,
# so the citation the model must emit is already in front of it.
context = "\n\n---\n\n".join(
    f"[{c['source']}, page {c['page']}]\n{c['text']}" for c in chunks
)

client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    output_config={"effort": "low"},        # extraction, not deep reasoning
    system=SYSTEM_PROMPT,                    # restriction + attribution + abstention
    messages=[{"role": "user",
               "content": f"Context:\n\n{context}\n\nQuestion: {query}"}],
)

The difference between asking a well-read colleague to answer from memory, and handing them five marked-up photocopies with the page numbers written in the margin, saying: answer using only these, cite which one, and tell me if the answer isn't in here.

Separation of concerns worth noticing The model is never asked to find anything — retrieval already did that, deterministically and cheaply. It is asked only to read, synthesise, and attribute. That split is what makes the system auditable: when an answer is wrong you can inspect the retrieved set and immediately tell whether retrieval failed to surface the evidence, or generation mishandled evidence it was given. Those are different bugs with different fixes.

Glossary

chunk
One independently retrievable unit of text, plus the metadata identifying where it came from.
embedding / dense vector
A fixed-length array of floats encoding a text's meaning as a position in a metric space. Here, 384 float32 values.
bi-encoder
An architecture that encodes query and document separately, so document vectors can be precomputed. Fast, but it never lets the two texts interact.
cross-encoder
Encodes query and document together for a far more accurate relevance score. Too slow to run over a whole corpus — hence its use as a second-stage reranker.
mean pooling
Averaging per-token vectors into one per-chunk vector. Cheap and effective, but it dilutes long passages.
cosine similarity
The cosine of the angle between two vectors; on unit-length vectors it equals their dot product. Range −1 to 1.
max_seq_length
The token ceiling of an encoder. Input beyond it is silently truncated — the source of the defect documented in step 3.
top-k / recall@k
Returning the k highest-scoring chunks; recall@k asks whether the correct chunk appears anywhere in that set.
exact vs. approximate (ANN)
Exact search compares every vector and is always right; ANN structures trade a little recall for sub-linear speed at scale.
citation grounding
Constraining the model to answer only from supplied context and cite its provenance — the primary hallucination control in RAG.
abstention
Explicitly licensing the model to say “not in the provided context” rather than inventing an answer.
closed-book vs. open-book
Answering from parametric memory versus from evidence supplied at inference time. RAG converts the former into the latter.
