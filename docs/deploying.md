# Deploying the demo

There are two deployments here and they are different products. Pick one before
reading further:

| | what a visitor gets | what it costs to run |
|---|---|---|
| **Static** (Vercel, Pages, any CDN) | the recorded questions, with the full pipeline behind each | a folder of JSON. No server, no models, free |
| **Live** (Spaces, Fly, Render) | any question they can type | a container with ~2 GB of RAM |

The static one is the better demo for most readers and the honest default: this
project is about showing *how* an answer was reached, and a recorded trace shows
that as completely as a live one. The live one exists because "type your own
question" is the thing people actually want to try.

---

## Static: recorded traces, no models

`python src/record_static.py --all` runs every golden-set question through the
real pipeline once, on a machine that has the models, and writes the exact
payload `/api/chat` returns for each. That payload holds every retrieval
stage with its ranking and scores, the fusion arithmetic, the reranker's
changes, what the cap dropped, the verdict and its threshold, and the term
attribution. Recording the ten
offered bird questions produces **0.5 MB**; all 157 golden-set questions across
three corpora is about **8 MB**.

Serving that needs nothing: it is JSON on a CDN. Every constraint in the table
below stops applying, because there is no Python at request time at all.

`--generate` additionally records prose from a local Ollama model, and stamps
the model name into the payload. **Attribute it wherever it is shown.**
"Generated by llama3.2" is a materially different claim from an answer written
by a frontier model, and a reader is entitled to know which one they have.

**What it loses, and a static build must say so rather than hide it:** a visitor
cannot ask a question that was not recorded. There is no model to answer one.
Presenting a text box that silently accepts only 157 strings would be worse than
presenting a list.

---

## Live: why not Vercel

If you want the text box to work, the answer has to be computed on demand, and
then Vercel does not work. The reasons are arithmetic rather than taste. The
process holds a FAISS index, a bi-encoder and a cross-encoder in memory:

| | this system | Vercel Python function |
|---|---|---|
| dependencies | **1,470 MB** (torch alone is 514 MB) | 250 MB limit |
| cold start | **~30 s** to load two models | 10 s timeout (Hobby) |
| memory between requests | required — the index stays loaded | none; every request starts cold |

Serverless is the wrong shape for this, not a tight fit. A function that reloads
half a gigabyte of torch to answer one question in a second would be slower and
more expensive than the laptop it was developed on.

**The same is true of Netlify Functions, Cloudflare Workers and Lambda at its
default limits.** What this needs is an ordinary long-lived process.

## What does work

| platform | why | notes |
|---|---|---|
| **Hugging Face Spaces** | built for exactly this: ML models, a persistent container, free CPU tier with enough RAM | Docker SDK, listens on **7860** — which is why the `Dockerfile` defaults there |
| **Fly.io** | small always-on VM, scales to zero if you accept a cold start | `fly launch` reads the Dockerfile; give it 2 GB |
| **Render / Railway** | the same shape, one-click from a repository | free tiers sleep, so the first visitor after idle waits ~40 s |

Hugging Face Spaces is the recommendation: the free CPU tier has the RAM, the
cold start is acceptable, and the audience for a project like this is already
there.

## Before you deploy

The repository contains **no documents and no index** in HEAD. They are
untracked, so a clone gives you the code and not the corpus. They remain in the
history, and `ATTRIBUTION.md` explains why. So the corpus has to be built once,
locally, before the image can be built:

```bash
python src/fetch_topic.py --topic birds        # Wikipedia -> data-birds/
RAG_STORE_DIR=store-birds RAG_DATA_DIR=data-birds python src/ingest.py
python src/check_golden.py --corpus birds      # labels still describe the corpus
```

That produces `data-birds/` and `store-birds/`, which the `Dockerfile` copies in.
Building the index inside the image instead would work, but it downloads from
Wikipedia at build time and makes the build non-reproducible.

**Which corpora go into a deployment is a licensing decision, not a technical
one.** The ornithology set is Wikipedia under CC BY-SA and redistributable with
attribution, so it can go anywhere. The recorded build ships the two arXiv
sets as short attributed excerpts; `ATTRIBUTION.md` measures what that amounts
to and argues the case. The source documents are not in this repository, and
deploying them *live* is a different question again: a live server will quote
any passage a visitor can reach, not the 2,700 that were recorded.

`--corpus birds` records one set only, which is the conservative build.

## Build and run

```bash
docker build -t rag-demo .
docker run -p 7860:7860 rag-demo
# then http://localhost:7860/
```

### Configuration

| variable | default | what it does |
|---|---|---|
| `PORT` | 7860 | the port to bind; container platforms set this |
| `RAG_HOST` | 127.0.0.1 | set to `0.0.0.0` in a container |
| `RAG_PUBLIC` | unset | `1` acknowledges that binding publicly is deliberate, and changes the startup warning to a statement of what is exposed |
| `RAG_CORPUS` | first indexed | which corpus to serve |
| `RAG_GENERATOR` | `anthropic` | `ollama` writes prose with a local model instead |

`RAG_PUBLIC` exists because the server refuses to be quietly public. Bound to
anything but loopback without it, it prints a warning; with it, it prints what a
visitor can read: passage text, document names, and the full trace of every
query. That is the correct list to think about before deploying a corpus.

## What a visitor can do

Everything, and that is intentional. There is no write path: no upload, no
indexing trigger from the browser, no authentication because there is nothing to
authenticate. `POST /api/index/start` rebuilds the index and **is reachable**, so
if you deploy this publicly and care, put it behind your platform's auth or
remove the route. For a read-only demo over Wikipedia articles, the exposure is
the corpus itself, which is already public.

## Cost

Free tiers are enough. The container is ~2 GB with models baked in, holds
~700 MB resident, and answers in about 100 ms warm and 900 ms cold. The front
page's own questions are pre-warmed at startup, so the first click is fast.
