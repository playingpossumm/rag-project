How this works.

A retrieval system built by hand, with every stage on screen.

Retrieval-augmented generation answers a question by searching a set of documents and quoting what it finds. A framework will build one in an afternoon, and it works, but every decision it makes is hidden inside it.

This system is built from parts instead. Each stage is drawn as it runs, each setting can be changed and the question re-run, and each default was chosen by measuring the alternatives. This page explains what the stages are.

Compared with a closed product

Five questions about the middle

NotebookLM, Glean and the enterprise search tools sold to companies will answer better than this. They have larger models and far more compute. They also answer from a closed middle: a question goes in, an answer comes out, and what happened in between is not shown. Here are five questions about that middle, and what each version can say.

Why did it return that?
Closed productThe passage arrives and how it was chosen is not exposed.
HereEvery stage is shown with the score it assigned, and asking a question draws what each retriever found, what the cross-encoder moved and what the cap dropped.
Did my change help?
Closed productNo numbers exist, so the judgement rests on an impression.
HereLabelled questions across three corpora are scored under every pipeline configuration, so a change is accepted or rejected on the measurement, and several were rejected.
What if it does not know?
Closed productIt answers anyway, in the same confident prose either way.
HereIt declines, below a threshold calibrated per corpus against questions the documents genuinely cannot answer.
What if the sources disagree?
Closed productThe disagreement is blended into one voice.
HerePassages from other documents are shown alongside, because the top result is sometimes the wrong one.
Can I put it in my own tool?
Closed productNo, because it is a destination rather than a component.
HereIt is a Python library with an HTTP wrapper around it, and this interface is one caller rather than the product.

Five changes that sounded obviously right were measured and dropped. Three of them:

  • Adding each document's title to every passage cost source recall. It was built, measured and reverted.
  • A reranker eight times larger fixed the same two questions the small one fixed. It took ten times as long.
  • Compressing the cross-encoder ran 1.5× faster and barely moved the rankings. It also made the system refuse questions it could answer.

The engineering log has all five, with their numbers.

A guide

Stage by stage

This site is a learning project. It was built to understand retrieval by making every part of it visible, rather than to serve documents at scale. Three prepared sets are searchable here, and they are fixed: 36 machine-learning papers, 45 ornithology articles, and 35 quantitative-finance papers. Each set had to be indexed, given labelled questions and calibrated before any number on this site could be measured.

To point it at your own documents, or to have it run the search live rather than replay a recorded one, run the project from GitHub. The repository also lists every document in all three sets.

Pick a document set, type a question, and the answer comes back with the passage it rests on and the route it took. Nothing is generated by default, so what you read is the retrieved text word for word. The whole path follows, in order.

The system can write the answer out instead, from those same passages, using a language model running on the machine that serves it. That is deliberately off here, because a written answer is one more place for something to go wrong between a document and a reader, and this site exists to show the retrieval. It has been measured separately and the analytics page reports what it is worth.

The answers cite their sources by filename. Every document in every set is listed with its title and format, and the whole system is open source. Every stage drawn on these pages is a function in that repository.

  1. The documents are cut into passages

    Each document is split into overlapping windows of about 210 tokens. A whole document is too large to compare against a single question. The windows overlap so that an answer sitting across a cut still appears whole in one of them.

  2. Two retrievers search, at the same moment

    Dense retrieval compares meaning, by turning the question and every passage into vectors. BM25 compares exact words, weighting rare ones heavily. Each one fails where the other works. Dense retrieval handles a question worded differently from its answer, and misses exact tokens such as a model number. BM25 finds those tokens immediately, and returns nothing when the question and the answer share no words. Running both covers each gap.

  3. The two rankings are fused

    Each retriever contributes 1/(60 + rank) to every passage it returned, and the sums are sorted. Only the position counts, never the score itself. The two retrievers measure different things on different scales, so adding their numbers together would require inventing a conversion between them.

  4. A cross-encoder re-reads the survivors

    The shortlist is scored again by a model that reads the question and the passage together and answers "does this passage answer this question". The earlier stages turned the question and the passage into numbers separately, then compared the numbers. This model reads the two together. It is more accurate and much slower, which is why it only sees a shortlist.

  5. At most two passages per document survive

    The diversity cap. This is a trade. It lowers the hit rate a little and raises how many of the answering documents come back. A question answered by four papers should not return four passages from one of them.

  6. The gate decides whether to answer at all

    If the best passage scores below this corpus's threshold, the system declines instead of answering. A search always returns its closest matches, however far away they are. Ask the ornithology set about tax law and it returns five passages about birds. The threshold is set for each set of documents by measuring where its real answers stop and its near-misses begin. What it catches is a question the documents cannot answer. What it does not catch is a wrong passage, because every question these three sets get wrong scores above its own set's threshold, so the gate is never consulted about them.

Reading what comes back

The passage is shown verbatim, with only the answering words in bold. The citation names the real document title and the location: a page for a PDF, a slide for a deck, a sheet for a spreadsheet.

The score comes from the cross-encoder and runs roughly −11 to +11. It is neither a probability nor a percentage, and it does not say whether the passage is right. It says how strongly the model matched this passage to this question, which is a different quantity. Across the three sets there are eleven questions where retrieval returns nothing correct, and nine of them score positive, the highest at +6.36. A strongly negative score does mean the documents probably do not hold the answer. A high one does not mean they do.

“Also found” lists passages from other documents that matched. The top passage is sometimes the wrong one. Asked for a bird's fused collarbone, the cross-encoder ranks the pygostyle passage first and the furcula second.

“The corpus does not contain this” means the gate declined. That is the system working. Some of the example questions on the front page are chosen to trigger it.

Why a passage and not a written answer. Everything above is text taken from a document, not prose composed for you. Composing it is the step where a system can state something no document said, so when this one does compose, the result is scored: whether it cites a document it was never given, whether it declines the questions the documents cannot answer, and how much of its wording came from the passages rather than from the model. No model judges those answers, because a judge is a second system whose own mistakes are invisible. The figures are on the analytics page.

Development

any-hit@5, ML papers

Nothing here was designed in one pass. Each stage was added because the one before it was measured and found wanting, and the figure beside each is the share of questions where a correct passage came back in the top five.

  1. Search by meaningkept

    Every passage becomes a vector, and the question is compared against all of them. This is the whole of what most tutorials build. any-hit 0.791

  2. Read the question and the passage togetherkept

    A second, slower model re-reads the shortlist one pair at a time. Comparing two separately-made vectors is cheap and blunt; reading the pair is expensive and much better at telling a passage that mentions the subject from one that answers the question. 0.791 → 0.806

  3. Search by exact words as wellkept

    Meaning-matching misses terms that carry their meaning by being exact, such as a model number or a species name. A second retriever scores word overlap, and the two rankings are merged. This was the largest single gain in the project. 0.806 → 0.866

  4. Cap each document to two passagesa trade

    One thorough document could fill every slot and hide a second document that also answered. The cap costs hit rate and buys coverage, and it is the only change here that was shipped while making a headline number worse. 0.925 → 0.910, documents found 0.745 → 0.785

And the half that did not survive. Eight changes that sounded obviously right were built, measured and taken out again. They are kept here because a reader learns more from them than from the four above, and because each was written before it was tested, which is the only way to find out that it does not work. The last three were this project's own planned next steps, named for months, and all three failed the first time they were measured.

  1. A reranker eight times largerrejected

    The obvious answer to "the reranker is the weakest stage". It recovered the same two questions the small one did and took ten times as long per query. Three models were compared, and the two halves of the job move in opposite directions as the model grows: the bigger ones rank worse and separate answerable from unanswerable better.

  2. Compressing the reranker to run fasterrejected

    1.5× faster, and the rankings barely moved, which is all a normal comparison would have checked. Every score also shifted down by a fifth of a point, and the threshold that decides whether to answer at all reads that score as an absolute. It silently started refusing questions it could answer.

  3. Putting each document's title on every passagereverted

    It should have helped a passage say what it belongs to. It bought no ranking gain and lost coverage. An earlier version had looked like a win, and that reading came from changing two things at once. documents found −0.051

  4. Expanding the query with words from the first resultsrejected

    The classical fix for a question whose answer uses different words. It recovered none of the twelve questions it was aimed at, for a reason that was written down before the run: the extra words come from the passages the first search returned, and the missing word is not in those either. 0 of 12 recovered

  5. Considering more candidates before rerankingrejected

    More candidates means the answer is available more often, and it was returned less often, on all three document sets. The reranker's precision falls faster than the extra candidates help. This is the clearest statement in the project of where the weak stage is, and it came out of an experiment about speed.

  6. Rewriting the question before searchingrejected

    Seven questions on the paper set fail no matter how the search is configured, and the plan for them was to have a language model restate the question more clearly first. It reached one of the seven and broke five questions the system had been getting right. A rewrite is a paraphrase, and paraphrasing a question that already works moves it off the wording that was working. net three questions worse, and six times slower

  7. Splitting the question into partsrejected

    The same seven, approached by breaking a question into its pieces, searching for each and combining the results. It reached none of them, cost the same three questions, and took twenty times longer per search. This had been the project's named answer for those seven for months, on an argument rather than a measurement. 0 of 7, at 21× the time

  8. Searching on an invented answerrejected

    The five questions no configuration reaches share a shape, in that the word which would find the passage is absent from the question. So a model was asked to answer from memory and the search was run on its invented passage, which supplies the vocabulary while the documents still supply the citation. Run on every question it is worse. On the paper set it recovers three and breaks seven, and on the finance set it recovers none and breaks four. paper set +3 / −7

    The repair was to run it only when the system was already about to decline, where it cannot disturb a question that works. That was measured before it was built, and it does not fire. Every one of the eleven questions these three sets get wrong scores above its own set's refusal line, the highest at +6.36, so the fallback would never once have run on the questions it was written for. reaches 0 of 11

    The reason is worth more than the experiment. The system is not uncertain when it is wrong. It reads a plausible wrong passage and scores it as highly as a right one, which is what makes these failures permanent, and it is not something a confidence number can expose. Three cheaper substitutes for the refusal line were tried on the same reasoning, being how many of the question's words appear in the passage, how far the top result leads the fifth, and how much the two searches agree. On all three the questions that fail sit inside the range of the questions that work, and catching all eleven means firing on 90% of every question asked.

  9. Showing each passage with its neighboursrejected

    When the answer is missing from what is shown it is usually close by, so the obvious repair is to show more. Each passage can carry the pieces either side of it, and the system already knows how. Everything shown, it puts the answer on screen for 9 more questions and multiplies the text by more than three, which is not a page anyone reads. Restricted to what the page would really render, which extends a passage backwards and not forwards, it is 4 questions for nearly twice the text. 0.808 → 0.840, at 591 → 1,073 characters a passage

    A refinement of it measured worse than doing nothing. Choosing which part to show from the enlarged passage rather than from the original scores 0.792 against 0.808, because the choice is made by where the question's words fall, and given more room it moves further from the answer.

  10. Neighbouring passages in the shortlistrejected

    Rather than show the neighbour, offer it to the model that ranks. The piece holding the answer is put in front of the reranker alongside the piece that was found, and the reranker decides. It gains one question on one set of documents, costs ranking quality on the other two, lets one more unanswerable question through the gate, and takes two and a half times as long. one question gained, MRR −0.012 and −0.015

  11. Scoring a passage on the passage around itrejected

    The same idea from the other end: rank each passage by the piece it sits in, while still returning the piece itself, so a paragraph is judged in context. Worse on every set of documents and on every measure but one. It does let fewer unanswerable questions through, and that is not an improvement: scoring against more text lowers every score at once, which moves the refusal line rather than improving the ranking, and it costs 7 answerable questions on the papers to buy. 0.910 → 0.881 on the papers, 0.939 → 0.818 on finance

  12. Cutting the documents into finer piecesrejected

    If no single passage holds both the words that find it and the words that answer, cut the documents so that one does. The pieces stay the same length and start closer together, which is 32% more of them to search. Measured on the ornithology set with the shortlist widened to match, it is worse at finding the answer and worse at showing it. 0.880 → 0.840 found, 0.760 → 0.720 shown

    It recovers exactly the one question the shortlist experiment above recovers, which is what says these are all reaching the same small set.

  13. A second meaning-model searching alongside the firstone set only

    Two different models reading the passages, their results combined. On a candidate shortlist it looked better on all three document sets. Measured on the finished answer it is worse on the papers, an even trade on the birds, and genuinely better only on the finance set, where it ships. The shortlist on the papers does not change at all: the same passages arrive in a different order, and the reranker does worse with that order.

  14. A larger model to write the answersno change

    Roughly three times the size and the same family, compared over the 43 questions both models answered. It gets two more of the 28 answerable ones right, which on a set this size is inside the noise, and everything else moves the other way. It misses one of the questions it should refuse, it quotes the papers' own reference numbers, which name no document and cannot be looked up, it draws less of its wording from the passages it was given, and it takes 58 times as long.

  15. Showing the part of a passage that answerskept

    The excerpt beneath each result began at the start of the passage, always. On the first page of a paper the start is the title, the authors and their addresses, so a question about the paper's subject was answered on screen with its letterhead, and the sentence that did answer sat just past the edge of what was shown. The excerpt now begins at the sentence carrying most of the question's words. Which passages are found did not change, so no figure on this page moved.

  16. Removing title pages from the searchleft off

    The obvious repair for the entry above, written before the cause was understood: drop a paper's title block from consideration. Measured, it scores worse on both document sets that have title pages, and the first reading was that it had been refuted. 0.851 → 0.836

    The whole of that drop is two questions out of 110, and the first reading of them was that the scoring had credited a title page, which answers nothing. Read in full they do answer, because a passage that begins with a title page continues into the abstract, and an abstract states a paper's finding in two or three sentences. Both of the two contain the answer outright.

    So the filter loses two real answers, and it loses them because dropping the first passage of a paper drops its abstract. It stays off. The correction is worth more than the experiment, since judging a passage by how it opens is the same error that put a title page on screen in the entry above.

The second pattern, and the reason the list above is long. Nine of these aim at the same two dozen questions, and they fail for one reason. The passage that answers does not contain the words of the question — that is why the search missed it. So putting it in front of the ranker changes nothing, because the ranker reads the same question and reaches the same conclusion, and showing more of the document around it, or cutting the document differently, or having a model invent an answer to search with, are all ways of offering the same passage again. A question that asks what something is called withholds the one word that would find it, and every part of this system that ranks, chooses or emphasises by the question's words moves away from the answer when given more room to look. That is a property of the question rather than of the documents, and no arrangement of the documents addresses it.

The pattern worth taking away. Four separate experiments improved what the first search finds and made the finished answer worse. Finding the answer and returning it are different problems, and a change that helps the first can cost the second. The clearest case is the second meaning-model: on the paper set the shortlist it produces is identical, and only the order changed.

Every one of these was written, run and measured before it was judged, which is why the list of what did not work is longer than the list of what did. Three of them were the planned next steps, and measuring them is how they stopped being plans.

Glossary

Terms used in this interface
RAG
Retrieval-augmented generation. Answering a question by searching a set of documents first and quoting what is found, rather than relying on what a model memorised. retrieval-augmented generation
Corpus
One set of documents, with everything derived from it: its index, its labelled questions, its threshold. Nothing about one corpus transfers to another. It is the finding this project has reused most. document set
Chunk
One passage: a window of about 210 tokens cut from a document, with 40 tokens of overlap onto its neighbour. passage
Locator
Where a passage came from, in the unit its format actually has: a page for a PDF, a slide for a deck, a sheet or section elsewhere. Saying “page 3” of a slide deck sends a reader somewhere that does not exist.
Embedding
A passage or question turned into a list of numbers, positioned so that things meaning similar things sit near each other. vector
Dense retrieval
Search by comparing embeddings. It matches meaning and handles a question worded differently from its answer. It misses rare tokens that carry their meaning by being exact, such as a model number. vector search · semantic search
BM25
Search by exact term overlap, weighting rare words far above common ones. The exact inverse profile: strong on identifiers, blind to paraphrase. sparse retrieval · lexical search
Fusion
Combining two rankings into one. This system uses reciprocal rank fusion: each retriever contributes 1/(60 + rank), so only position counts and no score conversion is needed. RRF · hybrid search
Candidate pool
The shortlist the first stage hands to the reranker. Its size is a latency dial: reranking is over 90% of the time a query takes and costs scale linearly with it. candidate_k
Cross-encoder
A model that reads a question and a passage together and scores whether one answers the other. Far more accurate than comparing two separately-made embeddings, and far too slow to run over a whole corpus. reranker
Reranking
Re-ordering the shortlist with the cross-encoder. On some corpora a fraction of the first stage's ordering is deliberately kept. When a question describes a term instead of naming it, the cross-encoder has little to work with.
Diversity cap
A limit of two passages per document in the final answer. Trades a little hit rate for covering more of the documents that answer the question.
Context expansion
Attaching the neighbouring passages to each result, so a sentence cut by a chunk boundary is still readable. It cannot change any ranking, because it runs after selection.
Abstention threshold
The score below which the system declines to answer, calibrated per corpus, because the same number that costs one corpus a single question costs another ten. It separates answerable questions from unanswerable ones rather than right passages from wrong ones. the gate · confidence threshold
Golden set
The labelled questions a corpus is scored against, each with the documents and locations that answer it. Every number on the analytics page comes from these.
Adversarial case
A question deliberately included because the documents cannot answer it. Refusing one is a success; answering it is the failure being measured. unanswerable case
any-hit@5
The fraction of questions where at least one correct passage appears in the five returned. Asks "did it find it at all".
MRR
Mean reciprocal rank. Rewards putting the right passage first: it scores 1.0 if the first passage is correct, 0.5 if the second is, and so on. mean reciprocal rank
NDCG
A ranking-quality score over all the relevant passages returned, not just the first, discounting each by how far down it sits. normalised discounted cumulative gain
Source recall
How many of the documents that answer a question were returned. The metric hit rate cannot express: returning one of four answering papers scores a perfect hit rate while missing three quarters of the answer.

Built by hand in Python: no retrieval framework, no CDN, no external request from this page. The server binds to localhost, since the documents may be private. A page about private documents should not call a font host, so the fonts are bundled.
